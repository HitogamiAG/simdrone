# Реальные полётные тесты Flight API

## Изолированный стенд

`docker-compose.flight.yml` переиспользует закреплённые образы проекта, но задаёт отдельные project/network, Gazebo partition, volume SQLite и не публикует порты. Набор запускает Backend, PX4 Hub, Gazebo, MediaMTX и тестовый контейнер. Он не монтирует исходники приложений: runner наследует собранный Gazebo image и содержит только тестовый harness.

Из корня репозитория:

```sh
sh backend/tests/flight/run.sh
```

Скрипт собирает и поднимает отдельный стек дважды, запускает проверки последовательно, сохраняет вывод и телеметрию в `artifacts/flight/`, затем удаляет только ресурсы Compose проекта `simdrone-flight-test`. Для работы нужны Docker Compose v2.24+ и свободные ресурсы для Gazebo и PX4 SITL. Файл `.env.flight` берётся из `.env.example` на время запуска и удаляется, если его не было до запуска. Скрипт сохраняет ранее существующие env-файлы.

Проверки меняют мир и поднимают реальные PX4 процессы. Не запускайте параллельно другой клиент, использующий этот тестовый Compose project. Рабочий `docker-compose.yml` не останавливается и не очищается.

## Наблюдение и доказательства

Runner отправляет команды только через публичный Backend HTTP/WebSocket API. Realtime `telemetry` и `flight` собираются отдельным подписчиком Backend; состояние модели дополнительно считывается независимой подпиской Gazebo Transport `/world/empty/pose/info` и статистикой мира. Gazebo Math через отдельный нативный helper проверяет преобразование станции из XYZ в WGS84, не повторяя формулу Hub.

Артефакт на каждый сценарий содержит команды и ответы без token, время по монотонным часам, телеметрию, PX4 process log stream, Gazebo-позы, world snapshot и runtime-диагностику. Runner также сохраняет Compose image IDs и stack logs. Таймаут наблюдателя и отсутствие свежих PX4 samples завершают сценарий ошибкой. При ошибке перед cleanup сохраняется диагностический снимок; cleanup не меняет исход pytest результата. PX4 ULog пока не извлекается и требует отдельного способа экспорта из Hub до удаления instance.

Базовые сценарии проверяют Offboard arm/нейтральный ввод/вертикальное движение/остановку/RTL и четырёхточечную миссию с replay `request_id`, MissionRaw progress, последовательным проходом точек, посадкой и disarm. Дополнительно проверяются реальный watchdog при открытом WS без ввода (остановка за 3 секунды, затем RTL) и отмена миссии после физического взлёта с идемпотентным повтором запроса. Критерии пути: waypoint — 2 м по горизонтали и 1,5 м по высоте; посадка — свежие `ON_GROUND`, `armed=false`, скорость менее 0,2 м/с в течение 2 секунд и расстояние до станции не более 3 м.

## Текущий статус и ограничения

04.10.2026 изолированный Compose прогон с пересборкой образов завершился **4 passed** за 209,50 с. Реальные PX4/Gazebo сценарии через публичный Backend: Offboard arm/neutral hold/вертикальный набор высоты/нулевые скорости/RTL; четырёхточечная MissionRaw миссия с наблюдаемым порядком XYZ, replay `request_id`, RTL и посадкой; открытый WS без ввода вызывает физическую остановку и RTL; отмена после наблюдаемого взлёта остаётся `returning` до подтверждённой посадки и disarm, повтор отмены идемпотентен. Независимые наблюдатели получали PX4 telemetry и Gazebo runtime-позы. Три protobuf deprecation warnings, ошибок тестов нет.

Второй чистый Compose-прогон 04.10.2026 завершился **3 passed, 1 failed** за 363,13 с. Offboard, stale-input watchdog и отмена миссии прошли. Основная четырёхточечная миссия осталась `active/mission`, `current_waypoint=0`; PX4 telemetry показала `flight_mode=HOLD`, а прямые Gazebo poses — неподвижание у станции на высоте около 5 м на протяжении 180 секунд. Тест завершился ошибкой таймаута, без автоматического повтора. Hub/MAVSDK сообщил `Mission changed`, но PX4 ULog и подробный PX4 процессный лог этой неудачи не были сохранены до удаления instance, поэтому причина отказа пока не локализована. Добавлена защита: после команды старта Hub ждёт входа в `MISSION` максимум 10 секунд и инициирует RTL при несовпадении. Эту защиту ещё не проверяли реальным полётом. Приёмка миссии считается нестабильной и блокирующей.

Пока не автоматизированы: потеря Backend, пауза/возобновление, отмена на этапах подготовки/загрузки, снимок миссии при редактировании/удалении, геопривязка с ненулевым origin/heading, независимость второго дрона, все знаки горизонтальных осей/yaw, ограничение скорости, восстановление ввода до RTL и lifecycle reset/reboot.

Сценарий завершения MAVSDK процесса намеренно не засчитан как реализованный: текущий Hub watcher при завершении MAVSDK также останавливает PX4. Тест полного failsafe должен сначала подтвердить, что PX4 остаётся живым после отказа MAVSDK. Приостановка MAVSDK через SIGSTOP требует отдельного хостового fault runner; Docker socket внутрь runner не передаётся.

Набор пока не подтверждает полный контракт Flight API и не является доказательством успешной приёмки. Проведены две чистые серии: первая прошла полностью, во второй выявлена нестабильность миссии. Требование о двух полных успешных прогонах и трёх последовательных базовых полётах каждого режима не выполнено. Перед следующей полевой серией harness должен сохранять PX4 ULog и process logs до удаления instance. Результаты проверок с адаптерами и SITL должны оставаться явно разделёнными.
