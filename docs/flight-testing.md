# Реальные полётные тесты Flight API

## Изолированный стенд

`docker-compose.flight.yml` переиспользует закреплённые образы проекта, но задаёт отдельные project/network, Gazebo partition, volume SQLite и не публикует порты. Набор запускает Backend, PX4 Hub, Gazebo, MediaMTX и тестовый контейнер. Он не монтирует исходники приложений: runner наследует собранный Gazebo image и содержит только тестовый harness.

Из корня репозитория:

```sh
sh backend/tests/flight/run.sh
```

Скрипт собирает и поднимает отдельный стек дважды, запускает проверки последовательно, сохраняет вывод и телеметрию в `artifacts/flight/`, затем удаляет только ресурсы Compose проекта `simdrone-flight-test`. Для одного сценария можно указать `FLIGHT_RUNS=1 FLIGHT_TEST_FILTER=mission_four_waypoints`; фильтр — pytest `-k`. Для работы нужны Docker Compose v2.24+ и свободные ресурсы для Gazebo и PX4 SITL. Файл `.env.flight` берётся из `.env.example` на время запуска и удаляется, если его не было до запуска. Скрипт сохраняет ранее существующие env-файлы.

Проверки меняют мир и поднимают реальные PX4 процессы. Не запускайте параллельно другой клиент, использующий этот тестовый Compose project. Рабочий `docker-compose.yml` не останавливается и не очищается.

## Наблюдение и доказательства

Runner отправляет команды только через публичный Backend HTTP/WebSocket API. Realtime `telemetry` и `flight` собираются отдельным подписчиком Backend; состояние модели дополнительно считывается независимой подпиской Gazebo Transport `/world/empty/pose/info` и статистикой мира. Gazebo Math через отдельный нативный helper проверяет преобразование станции из XYZ в WGS84, не повторяя формулу Hub.

Артефакт на каждый сценарий содержит команды и ответы без token, время по монотонным часам, телеметрию, отфильтрованные PX4 process logs, Gazebo-позы, world snapshot и runtime-диагностику. Отдельный Compose volume временно хранит каталог PX4 instance; до cleanup runner копирует `.ulg`, `mavsdk.log` и строки PX4 с уровнями INFO/WARN/ERROR. ULog разбирается закреплённым `pyulog==1.2.3`, включая сообщения PX4 и хвост `mission_result`. Runner также сохраняет Compose image IDs и stack logs. Таймаут наблюдателя и отсутствие свежих PX4 samples завершают сценарий ошибкой. При ошибке перед cleanup сохраняется диагностический снимок; cleanup не меняет исход pytest результата. Артефакты и ULog остаются только в игнорируемом `artifacts/flight/`.

Базовые сценарии проверяют Offboard arm/нейтральный ввод/вертикальное движение/остановку/RTL и четырёхточечную миссию с replay `request_id`, MissionRaw progress, последовательным проходом точек, посадкой и disarm. Дополнительно проверяются реальный watchdog при открытом WS без ввода (остановка за 3 секунды, затем RTL) и отмена миссии после физического взлёта с идемпотентным повтором запроса. Критерии пути: waypoint — 2 м по горизонтали и 1,5 м по высоте; посадка — свежие `ON_GROUND`, `armed=false`, скорость менее 0,2 м/с в течение 2 секунд и расстояние до станции не более 3 м.

## Текущий статус и ограничения

04.10.2026 после исправлений изолированный Compose прогон с пересборкой образов завершился **4 passed** за 296,17 с. Через публичный Backend на реальных PX4/Gazebo прошли Offboard arm/neutral hold/вертикальный набор высоты/нулевые скорости/RTL; четырёхточечная MissionRaw миссия с последовательным наблюдением XYZ, replay `request_id`, RTL, посадкой и disarm; watchdog при открытом WS без ввода (остановка и возврат); отмена миссии после физического взлёта с идемпотентным повтором и подтверждённой посадкой. Независимо собирались PX4 telemetry и Gazebo runtime-позы. ULog итоговой миссии показывает `mission_result.seq_reached=4`, текущий терминальный RTL item, а затем `RTL: land at destination`, `Landing detected` и `Disarmed by landing`. Три protobuf deprecation warnings; тесты прошли.

Первоначальный прогон с `3 passed, 1 failed` не сохранил PX4 ULog, поэтому точный путь исходного отказа теперь восстановить нельзя. На следующем реальном повторе ULog выявил дефект завершения MissionRaw: PX4 v1.16 достиг waypoint 4, затем выставил последним активным item RTL (`seq_current=5`, `seq_total=6`) и перешёл к возврату, но не выставил `mission_result.finished=1`. Hub ждал только `current >= total`, поэтому оставлял execution в `active/mission`. Код теперь считает подтверждённым завершением маршрута переход PX4 в RTL после достижения всех waypoint и затем ждёт посадку у станции; ранняя посадка до прохождения всех точек завершает execution ошибкой. Тест также исправлен: ожидаемый RTL после всех точек не считается отсутствием `MISSION`.

Во время повторного полного прогона был обнаружен отдельный дефект watchdog: после `Offboard.stop()` PX4 оставался в `HOLD`, хотя Hub уже отправил `return_to_launch()` и сообщил `returning`. ULog показал, что аппарат оставался armed и в HOLD у станции; посадки не было. Теперь Hub повторяет RTL-команду раз в секунду, пока телеметрия не подтвердит RTL или посадку. Целевой реальный watchdog тест прошёл за 88,90 с, затем весь набор прошёл **4/4**. Первый прогон с новым маршрутом до этого завершился ошибкой именно из-за тестового guard: он не принимал ожидаемый RTL после waypoint; ULog помог отличить это от отказа PX4. Автоматического повтора упавшего теста не было.

Для полного набора ещё нужны реальные проверки: все знаки forward/right/up/yaw и движение после поворота на 90°; диагональный ввод и PX4 limits; второй владелец, чужой token, повторная сессия, DELETE и land в текущем месте; восстановление ввода до RTL, повторный `seq`, резкий разрыв телефона; потеря Backend отдельно во время Offboard и миссии; автономность миссии при отключении клиента, редактирование/удаление определения с неизменностью снимка; отмена во время подготовки/загрузки; геопривязка с ненулевым origin, elevation и heading=90°; два независимых дрона; pause/resume для миссии, вооружённой и невооружённой сессий; reset/delete/restart/reboot и инвалидирование старых поколений; приостановка и аварийное завершение MAVSDK с разбором failsafe PX4. Весь набор должен пройти дважды с чистого стенда, базовые миссия и Offboard — по три последовательных полёта без reset между успешными посадками.

Аварийное завершение/приостановка MAVSDK не проверялись. Известный риск остаётся: текущий Hub watcher при завершении MAVSDK также останавливает PX4. Перед таким тестом нужно изменить/подтвердить владение PX4, иначе отказ gateway завершит автопилот вместо проверки его собственного failsafe. Инъекция через SIGSTOP должна выполняться хостовым runner; Docker socket внутрь контейнера не передаётся.

Текущие исправления подтверждены одним успешным полным SITL набором и отдельным целевым повтором watchdog; это ещё не полная приёмка. Требование о двух полных успешных прогонах и трёх последовательных базовых полётах каждого режима не выполнено. Непроверенные сценарии перечислены выше. Результаты контрактных проверок с адаптерами и настоящих полётов должны оставаться явно разделёнными.

Сопутствующие проверки 04.10.2026 в Docker: PX4 Hub suite — **46 passed**; ранее прогнанные Backend выбранные контракты — **19 passed**; Gazebo Service contract — **15 passed**, `regression.py` и `smoke.py` прошли на изолированном стенде. `docker compose config --quiet`, shell syntax, Python compile и сборка изменённых образов прошли. Контрактные проверки не заменяют перечисленные незапущенные реальные сценарии.
