# Flight API: план и состояние реализации

## Статус

Реализация частичная. Критерий завершения согласованного плана **не выполнен**. Аудит коммитов `db17e3b` и `c4dbe6a` выявил нарушения контракта и недостаточное тестовое покрытие. Подробности и воспроизводимые проверки: [flight-api-audit.md](flight-api-audit.md).

## Целевой контракт

Backend предоставляет публичные ID и Flight API, сохраняет определения миссий с ревизиями в SQLite на именованном volume и согласует принятие команд с lifecycle. Hub владеет единым выполнением `mission` или `offboard`, MAVSDK-командами, подтверждением состояния, эксклюзивной сессией и watchdog. Миссия загружается целиком в PX4; браузер не участвует в исполнении маршрута.

Миссии задаются XYZ мира Gazebo. Hub должен преобразовывать их в WGS84 согласно действующим origin, elevation и heading, проверять станцию и наблюдаемый home. Успех или отмена подтверждаются свежей телеметрией посадки у станции и disarm. Приём команды и достижение результата — отдельные события.

Offboard задаёт скорости через `VelocityBodyYawspeed`: до 3 м/с горизонтально, до 1 м/с вертикально и до 60°/с yaw, с учётом ограничений PX4. Arm не взлетает автоматически. Без ввода 0,5 с задаются нулевые скорости, через 5 с начинается RTL с отзывом сессии. Потерю Hub/MAVSDK обрабатывает отдельно настроенный и подтверждённый failsafe PX4.

Изменяющие запросы проверяют `request_id` и ожидаемое поколение instance. Повтор с тем же содержимым возвращает исходную операцию; другое содержимое даёт `409`. Lifecycle сначала инвалидирует сессии, callbacks и задачи, затем выполняет прежние stop/reset/delete/reboot. Пауза отзывает ручное управление и прекращает последнее движение; после resume требуется возврат или disarm на земле. Автоматического восстановления выполнения нет.

## Этапы

| Этап | Текущее состояние | Что осталось |
| --- | --- | --- |
| Основа Hub | FlightController, команды MAVSDK и штатный watchdog добавлены | Обработка отказов, единое состояние исполнения, подтверждения и failsafe; проверка прямого Offboard-взлёта |
| Offboard через Backend | HTTP/WS-маршруты и прокси добавлены | Владение, эксклюзивность, отзыв сессии, идемпотентность; проверка публичного пути |
| Миссии | SQLite, CRUD, ревизии, код MissionRaw добавлены | Heading, replay, поколения и подтверждение посадки; проверка запуска, прогресса и отмены |
| Lifecycle | Вызовы cleanup добавлены | Гонка принятия с закрытием; active flight reset/restart/stop, pause/resume и отказы процессов |
| Документация и приёмка | Статус и описания уточнены после аудита | Capabilities должны отражать проверенную готовность; сквозные проверки и описания OpenAPI |

## Доказанное и непроверенное

Существующие Docker-наборы проходят: Backend — **18 passed**, Hub — **33 passed**. В них новых тестов Flight API только **2** и **6** соответственно. Это тест SQLite, регистрация маршрутов, две проверки собственной формулы координат, ограничение скорости, штатная ветка watchdog и возможность RTL при потерянной привязке. Покрытие конфликтов, token/seq, запуска/отмены миссии и активного cleanup этими наборами не подтверждается.

Дополнительные проверки аудита выявили **9 нарушений Hub и 3 Backend**, завершились с кодом **1**. Они используют подменённые зависимости и не являются реальными полётами. Нативная библиотека Gazebo независимо подтвердила неверный знак heading в текущем Hub.

Реальные полёты, потеря телефона/Backend/Hub, посадка у станции, повторный запуск, два дрона и active lifecycle не проверены. В checkout нет `third-party`, требуемого Dockerfile Gazebo Service; полный Compose-прогон не выполнялся. Это объясняет отсутствие сквозной проверки, но не означает завершения плана.

React-карта, интерфейс джойстика, обход препятствий, точная посадка по метке и сохранение истории выполнений между runtime остаются за пределами MVP.
