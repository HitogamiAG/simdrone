# Frontend MVP: рабочее пространство карты Gazebo

## Цель и стек

Одна страница: сворачиваемая панель управления слева, 2D/3D карта справа, динамические окна поверх карты. Язык — русский, тема — тёмная. Целевая область 1440×900, минимальная 1280×720. Страница не прокручивается целиком; списки и содержимое окон прокручиваются внутри своих областей.

Стек уже установлен и закреплён в [`frontend/package-lock.json`](../frontend/package-lock.json): React 19.3.0 / React DOM, TypeScript 7.0.2, Vite 8.3.2; Mantine 9.6.3 (Core, Hooks, Form, Notifications), Zod 4.6.5; Three.js 0.186.1, React Three Fiber 9.8.1, Drei 10.7.9; react-rnd 10.5.3; TanStack Query 5.104.1; Zustand 5.0.15; Tabler Icons React 3.48.0. Проверки: Vitest 5.0.3, React Testing Library и Playwright 1.63.0.

Docker-сервис публикует production-сборку на `http://localhost:3000`; Vite dev server — порт 5173. Оба проксируют `/api` и WebSocket в Backend на 8003. WHEP остаётся по настроенному прямому адресу MediaMTX.

Окно телеметрии показывает pose Gazebo и образцы PX4 своего дрона. Окно логов получает live stdout/stderr PX4 с поиском, паузой отображения, очисткой и буфером 2000 строк. Видеоокно выбирает камеру и выполняет WHEP SDP handshake, очищает peer/session при закрытии; декодированный кадр ещё не проверен в браузере с реальной камерой. Кнопки миссий ещё не подключены.

### Готовые предпосылки со стороны мира и API

- [x] `GET /api/v1/world/spawn-pads` возвращает каталог, координаты и готовую spawn-позу; Backend дополняет доступность и владельца.
- [x] Публичное создание требует `spawn_pad_id`; Backend закрепляет площадку до подтверждённого удаления дрона. Ответы содержат `spawn_pad_id`, `initial_pose`, текущую `simulation.pose`.
- [x] Отдельные реальные Docker/SITL проверки прошли: спаун и контакт шасси на обеих площадках с PX4 `ON_GROUND`, освобождение после удаления; Offboard с вертикальным движением/удержанием/RTL; одновременные Mission и Offboard у двух дронов; миссия по четырём точкам с возвратом и повтором.

Пакет больше не требуется создавать с нуля, а браузер подключён к его локальным GLB и manifest. Пространственная приёмка GLB/Gazebo с допуском 2 см остаётся открытой. Пройденные API/SITL сценарии не заменяют браузерную приёмку, полный lifecycle-набор и повторные полётные прогоны.

## Компоновка и оформление

Левая панель: 360 px, свёрнутая — 56 px. Карта занимает остаток ширины и всю высоту. Верх панели: название приложения и кнопка сворачивания. Низ: индикатор сервисов, открывающий диагностический Modal. Accordion-блоки независимы; изначально раскрыты «Дроны» и «Миссии». В свёрнутом состоянии остаются три кнопки с tooltip; нажатие раскрывает нужный блок.

Фон `#141517`, панель/окна `#1F2125`, заголовки `#272A30`, границы `#393D45` (1 px), текст `#F1F3F5`, вторичный текст `#ADB5BD`, действие `#4DABF7`. Готовность — зелёный, ожидание/связь — жёлтый, ошибка — красный; цвет сопровождается текстом/значком. Цвет дрона обозначает идентичность, badge — состояние. Отступы 4/8/12/16/24 px, скругления 6 px у контролов и 8 px у окон. Локально поставляемый Inter, основной текст 14 px, подписи 12 px. Без декоративных теней; короткие переходы раскрытия и фокуса.

Все выборы ресурсов, настройки и подтверждения — Mantine Modal. Успехи — Notifications, ошибки формы — у полей; недоступные действия имеют пояснение причины. Модальные диалоги и меню располагаются выше динамических окон.

## Оставшиеся этапы реализации

Каждый этап завершается отдельным Git-коммитом, актуализацией frontend README и проверками своего поведения. Изменяющие мир сценарии запускаются последовательно в Docker.

### 1. Контракты, HTTP и общий realtime-клиент

- [ ] Вынести из монолитного `App.tsx` API-клиент, типы, доменные компоненты панели, карту и менеджер окон. Данные API проверять схемами; ошибки показывать с `code`, `message` и полезными `details`.
- [ ] TanStack Query: мир, status, дроны, площадки, миссии, исполнения, сенсоры. Zustand: выбранные ресурсы, черновик миссии, настройки камеры/слоёв, окна. Не дублировать серверный реестр в локальном состоянии.
- [x] Один realtime WebSocket для карты и окон: subscribe/unsubscribe с подсчётом потребителей, reconnect и маршрутизация по каналу.
- [x] Сохранять последние образцы на канал/тип; поздние события после закрытия последнего потребителя не доставляются. Карта использует pose, телеметрия — PX4 telemetry, окно логов — ограниченный PX4 logs.
- [x] Сверять runtime generation на callbacks pose, telemetry и logs; invalidation/error очищает текущий sample и повторно подписывает живых потребителей. Проверку world generation и каналы sensor/flight/world.logs ещё добавить.
- [ ] Отслеживать поколения, invalidation и свежесть данных. Reset/delete прекращают старые потоки; world-reset удаляет окна прежних дронов. После перезапуска Backend перечитывать реестр и диагностику.
- [ ] В управляющих API, поддерживающих `request_id`, сохранять ID одной операции при повторе; не повторять команды автоматически с новым ID. Не добавлять поля в запросы, если контракт их не поддерживает.
- [ ] Разделять принятие команды и подтверждённый результат; при потерянном ответе перечитывать состояние, не объявлять успех/освобождение заранее.

Готовность этапа: карта и несколько окон разделяют подписки, смена выбора не оставляет старые данные, reconnect/reset/delete корректно обновляют состояние. Общий клиент и поток поз работают; поколения и подписки окон требуют завершения вместе с их содержимым.

### 2. Создание и закрепление площадок

Диалог создания и выбор с карты реализованы: каталог опрашивается у Backend, свободные площадки выбираются явно, занятые/недоступные показывают причину и владельца, координаты только для чтения, запрос использует `spawn_pad_id`. Ошибки конфликта обновляют каталог; список дронов показывает закреплённую площадку. Остаются детальные состояния lifecycle/failed и браузерная интеграция с настоящим Backend/Gazebo.

#### Панель и диалог

- [ ] В блоке «Дроны» показывать число ресурсов, цвет, имя, состояние полёта, PX4, закреплённую площадку, меню и отдельную кнопку центрирования. Failed-записи сохранять с этапом ошибки и доступными действиями восстановления.
- [x] Заменить форму XYZ/yaw диалогом «Создать дрон»: имя, фиксированная модель `x500_gimbal`, обязательный выбор площадки. Удалить ручной ввод позиции и ориентации и старое преобразование экранных координат в условные метры.
- [x] Каталог брать **из публичного API**, не из manifest. Строка площадки: имя/ID, доступность, владелец, XYZ верхней поверхности и готовая spawn-поза. Координаты и направление доступны только для чтения; они задаются SDF.
- [x] Занятые и недоступные площадки оставлять видимыми, выбор отключать с причиной. Показывать загрузку, ошибку/повтор и состояние «нет свободных площадок». Предварительный выбор в UI не резервирует площадку.
- [x] Отправлять `{model: "x500_gimbal", name, spawn_pad_id}`. На время запроса блокировать повторную отправку. После ответа перечитывать дроны и каталог, выбирать созданный дрон.
- [x] Обрабатывать `404 spawn_pad_not_found`, `409 spawn_pad_occupied`, `409 spawn_pad_unavailable` и ошибки полей `422`. При конфликте обновлять каталог и сохранять имя; требовать новый доступный выбор, не выбирать площадку автоматически.

#### Карта и lifecycle

- [x] Поверх существующей геометрии GLB отображать слой «Площадки»: ID, состояние, владельца и направление спауна. Не создавать вторую геометрическую копию площадки. Рамка/подпись и текст позволяют различать состояние без опоры только на цвет.
- [x] В диалоге кнопка «Выбрать площадку на карте» временно скрывает Modal и включает режим выбора. Клик по свободной площадке возвращает диалог с её ID; занятая показывает причину. «Отмена» восстанавливает диалог и прежний выбор. Это выбор существующей площадки, координаты не редактируются.
- [x] Обычный клик по площадке показывает Modal с её параметрами; доступны «Создать дрон» для свободной или «Выбрать владельца» для занятой. Выбор площадки не добавляет точку маршрута; режимы карты взаимоисключающие.
- [ ] При взлёте, посадке, остановке PX4, drone-reset и sensor-reset сохранять отображение закрепления. Drone-reset возвращает сохранённую `initial_pose`; текущая поза всегда берётся из наблюдений.
- [ ] Освобождение показывать после подтверждённого удаления записи Backend. Failed/неполное удаление сохраняет владельца. После подтверждённого world-reset/reboot перечитывать весь каталог.
- [ ] При неучтённых ресурсах после рестарта Backend показывать `unavailable` и диагностическое объяснение; согласованный reset мира выполняется через подтверждение с последствиями.

В `empty` две площадки: основания `(-3, 0, 0)` и `(3, 0, 0)`, поверхность Z=0,3 м, spawn-frame для текущего `x500_gimbal` Z=0,292 м. Эти значения описывают текущую поставку; UI не вычисляет их самостоятельно и поддерживает произвольное число площадок из API. Дрон создаётся с зазором и оседает на шасси; начальная и наблюдаемая позы могут немного отличаться.

Готовность этапа: выбор обязателен, конкурирующее создание корректно обрабатывает `409`, площадка остаётся занятой весь lifecycle владельца и переиспользуется только после успешного удаления. Диалоговый и карточный выбор реализованы; полный lifecycle и реальная интеграционная приёмка остаются открытыми.

### 5. Динамические окна и реальные потоки

Оболочка общая: имя дрона и тип, связь, свернуть/развернуть/закрыть, drag за заголовок, resize за границы. Одна пара «дрон + тип» — одно окно; повторное открытие поднимает его наверх.

| Окно | Старт / минимум | Оставшееся содержимое |
|---|---|---|
| Телеметрия | 360×360 / 300×240 | XYZ Gazebo, скорость PX4, ориентация, режим, armed, landed, GPS, health, батарея при наличии; данные собственного дрона |
| Видео | 480×320 / 320×220 | Выбор камеры, WHEP offer/answer и cleanup реализованы; нужно проверить сохранение пропорций и реальный декодированный кадр в браузере. |
| Логи | 640×320 / 360×220 | Live PX4 поток, источник/время, поиск, автопрокрутка, пауза отображения, очистка и буфер 2000 строк реализованы; нужна проверка браузером с настоящим PX4 |
| Ручное управление | 440×420 / 400×380 | Сессия, захват ввода, arm/disarm, направления, лимиты, RTL/посадка, связь и watchdog |

- [ ] Сохранение координат/размеров/сворачивания локально; восстановление только для существующих дронов. Offboard-сессии и токены не восстанавливаются.
- [ ] Коррекция положения после resize браузера/панели: заголовки остаются доступны, окна ограничены картой; корректные минимальные размеры для каждого типа.
- [x] Сворачивание телеметрии/логов сохраняет подписку; закрытие окна освобождает канал.
- [x] Общие подписки не закрываются, пока у них есть другой потребитель. Окно берёт поток по собственному drone ID.
- [x] Сворачивание/закрытие видео освобождает WHEP session, AbortController и RTCPeerConnection; открытие создаёт новую сессию.
- [ ] Логи мира открываются из панели мира отдельным окном с источником world и теми же правилами буфера/cleanup.

Готовность этапа: нет дублей и утечек, окна работают на обоих целевых размерах, собственные данные не смешиваются; видео подтверждено реальным декодированным кадром браузера.

### 6. Ручное управление, настройки и lifecycle

- [ ] Отдельный Offboard WebSocket, нормализованные оси, возрастающий `seq`, 20 Гц. WASD относительно корпуса, R/F вверх/вниз, Q/E поворот; движение только при удержании Space либо экранной кнопки.
- [ ] Ввод только после явного захвата; поля форм не управляют дроном. При отпускании — нулевые скорости, при потере фокуса — нулевая команда и прекращение ввода; повторный захват явный.
- [ ] Arm явный и не инициирует взлёт; disarm только после подтверждённой посадки. Закрытие активной сессии — подтверждение возможного RTL Backend. При потере связи показать watchdog: остановка через 0,5 с, RTL через 5 с.
- [ ] Modal настроек дрона: разрешённые поля PX4, сенсоры и lifecycle. Параметры PX4 не сбрасывают физику; sensor-reset/drone-reset пересоздают дрон с сохранённой площадкой и начальной позой.
- [ ] World Modal: physics, gravity, геопривязка — только поддерживаемые поля API. Применение выполняет world-reset и затем настройки; reset/reboot/удаление требуют подтверждения с количеством затронутых дронов и последствиями.
- [ ] Диагностика сервисов: фактическая готовность каждого сервиса, текущая операция, failed и неучтённые ресурсы. HTTP 200 от status не означает готовность всех сервисов.

Готовность этапа: реальный ручной полёт и потеря фокуса/связи, все подтверждения и корректное обновление дронов, площадок, подписок и окон после lifecycle операций.

### 7. Браузерная приёмка и документация

- [ ] Компонентные/контрактные проверки форм, каталога площадок, ошибок, черновиков, окон и подписок; сборка и lint.
- [ ] Playwright с реальными Backend/Gazebo/PX4/MediaMTX в Docker; сценарии reset/полётов запускаются последовательно.
- [ ] Frontend README: запуск, локальные assets, API/потоки, конфигурация, ограничения и фактически пройденные проверки. План обновляется по завершённым критериям.

| Область | Обязательный браузерный сценарий |
|---|---|
| Геометрия | Локальный GLB, контрольные точки ≤2 см, оси/масштаб/высоты площадок, направление маркеров, несовместимый пакет |
| Площадки | Диалоговый выбор и выбор на карте, занятая/недоступная, конфликт двух клиентов, оба спауна, закрепление после полёта/reset, повторное использование после удаления |
| Миссии | Точки/XYZ/порядок, 2D↔3D, dirty/ревизии, проверка, реальный прогресс/возврат/отмена/повтор |
| Окна | Drag/resize/focus/уникальность, сворачивание, локальное восстановление, bounds на 1280×720 и 1440×900 |
| Realtime | Общие потребители, свежесть, reconnect, поколения, reset/delete, отсутствие старых callbacks |
| Offboard | Клавиатура и экранные кнопки, отпускание, поля форм, потеря фокуса/соединения, закрытие сессии |
| Видео и логи | Реальный decoded frame, закрытие/повторное открытие/WHEP cleanup; реальные строки и ограничение буфера |
| Lifecycle | Pause/resume, PX4-параметры, sensor/drone/world-reset, reboot, failed cleanup и неучтённые ресурсы |

MVP принимается после выполнения этих браузерных сценариев с настоящими сервисами. Пройденные unit-тесты и отдельные SITL-проверки не закрывают эту приёмку.

## Запуск и границы MVP

Разработка: `cd frontend && npm ci && npm run dev`. Проверки: `npm test`, `npm run build`, `npm run lint`. Production: `docker compose up --build frontend`, порт 3000. Поведение контрактов описано в [`backend/README.md`](../backend/README.md) и [`gazebo-service/README.md`](../gazebo-service/README.md); правила экспорта — в [`models/empty/README.md`](../models/empty/README.md).

Мобильный интерфейс, геймпады, географические подложки, обход препятствий, точная посадка по ArUco и загрузка произвольных моделей через UI остаются вне MVP. Площадки определяются SDF поставки; frontend выбирает существующие площадки, но не создаёт и не перемещает их.
