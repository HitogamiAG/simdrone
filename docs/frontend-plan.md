# Frontend MVP: рабочее пространство карты Gazebo

## Цель и зависимости

React 19 + TypeScript 7 + Vite 8; Mantine 9 для контролов и диалогов; React Three Fiber 9 / Three.js 0.186 для общей сцены; react-rnd для окон; TanStack Query для HTTP; Zustand для состояния рабочего места; Zod для проверки форм; Tabler Icons. Пакеты и lockfile фиксируют версии. Docker-сервис публикует production-сборку на `http://localhost:3000`; Vite dev server — порт 5173, проксирует `/api` и WebSocket в Backend на 8003.

Целевая область 1440×900, минимальная 1280×720. Приложение не прокручивается целиком; списки и содержимое окон прокручиваются внутри своих областей.

## Состояние реализации

- [x] Одностраничный каркас, тёмная тема, сворачиваемая панель и блоки «Дроны», «Миссии», «Настройки мира».

- [x] API идентичности статического пакета `GET /api/v1/world/map`; корректное состояние «пакет отсутствует».

- [ ] Blender-пакет участка: `.blend`, `world.glb`, SDF/ресурсы/коллизии и manifest. Он отсутствует в текущем репозитории; карта намеренно заблокирована до его приёмки.

## Компоновка и стили

Экран: фиксированная боковая панель 360 px (свёрнутая 56 px) и карта на всю оставшуюся площадь. Верх панели показывает имя рабочего пространства и кнопку сворачивания; нижняя строка показывает доступность Backend. Accordion блоки независимы и могут быть раскрыты одновременно; по умолчанию раскрыты дроны и миссии.

Фон `#141517`, панель/окна `#1F2125`, заголовки `#272A30`, границы `#393D45`, основной текст `#F1F3F5`, вторичный `#ADB5BD`, действие `#4DABF7`. Состояния дрона сопровождаются текстом; оттенок маркера предназначен для идентичности. Сетка 4/8/12/16/24 px, скругления 6 px для контролов и 8 px для окон. Без декоративных теней и анимации.

Панель дронов показывает имя, состояние, PX4 и выбор; контекстное действие открывает телеметрию. Создание дрона требует x500_gimbal, имя, XYZ и ориентацию; указание позиции на карте временно скрывает диалог. Панель миссий показывает сохранённые ресурсы и точку входа к созданию/выбору. Настройки мира показывают имя и состояние и предоставляют места для pause/resume и подтверждаемых операций reset/reboot.

Карта занимает весь workspace. Сверху слева переключатели 2D/3D, масштаба, участка, выбранного дрона и follow; справа — слои дронов/маршрутов/сетки; снизу — координаты XYZ Gazebo в метрах и dock свёрнутых окон. 2D — ортографический вид сверху, 3D — перспектива. Управление картой не должно перехватывать действия окон и манипуляторов. До Blender-пакета показывается причина блокировки, а команды создания/полёта отключены.

Окна привязаны к паре drone+type, повторное открытие поднимает существующее окно. Перемещение выполняется за заголовок, изменение размера — за границы; оболочка ограничена картой. Стартовые размеры: телеметрия 360×360, видео 480×320, логи 640×320, manual 440×420. В production дополнить persistence размеров/позиции только для существующих дронов. Видео сворачивается с освобождением WHEP, телеметрия/логи сохраняют подписку; логовый буфер не превышает 2000 строк.

## Blender-пакет и система координат

Карта не должна изображать условный мир вместо участка. До интеграции требуются исходный Blender файл с применёнными transforms и метрами, браузерный `world.glb`, SDF Gazebo и ресурсы/коллизии из того же исходника, manifest и описание экспорта. Пространство дронов — Gazebo XYZ, метры, Z вверх. Manifest задаёт идентификатор/версию/имя мира, bounds, единицы, преобразование GLB↔Gazebo и минимум три контрольные точки. Приёмка проверяет оси, масштаб, начало координат, поверхности и соответствие визуальных объектов коллизиям с точностью контрольных точек 2 см; Gazebo плагины сохраняются. Все ресурсы локальные.

`GET /api/v1/world/map` читает `/world-model/manifest.json` (переопределяется `WORLD_MAP_MANIFEST`). Он возвращает только identity/координатную метаинформацию, без геометрии; отсутствующий или некорректный manifest возвращает `available: false`. GLB поставляется браузеру локально. Старт/ручное управление заблокированы, если идентичность поставки не подтверждена.

## Состояние и протоколы

TanStack Query держит REST ресурсы; Zustand — выбранный дрон, режим карты и динамические окна. Один `/api/v1/realtime` клиент карты подписывается на `drone.{public_id}.pose`; формат конверта и generations описан в Backend README. PoseTracker отдаёт snapshot существующей подписки, без нового Gazebo Transport listener. Повторный запуск Backend требует перечитывания списка ресурсов. Принятие управляющего запроса следует показывать отдельно от подтверждённого runtime состояния.

Все управляющие запросы должны иметь уникальный `request_id`; повтор с новым id автоматически не посылать. Offboard использует отдельный WS, seq и частоту 20 Гц. Видео — нативный `RTCPeerConnection` через WHEP; воспроизведение подтверждается browser decoded frame. Ручной ввод: WASD, R/F, Q/E; непрерывное движение только при зажатом Space или кнопке экрана. Потеря фокуса прекращает ввод и посылает нулевую скорость; повторный захват явный. Эти протоколы пока не подключены к frontend-компонентам.

## Проверка и запуск

Разработка: `cd frontend && npm ci && npm run dev`. Проверка: `npm test`, сборка: `npm run build`, lint: `npm run lint`. Production: `docker compose up --build frontend`; интерфейс `http://localhost:3000`, Backend проксируется nginx через `/api`, включая WebSocket. WHEP остаётся по настроенному прямому адресу MediaMTX. Playwright установлен для будущих browser сценариев с реальными сервисами, но e2e-набор пока отсутствует.

Приёмка полной карты и MVP блокируется до получения Blender-пакета и реальных браузерных сценариев с Gazebo/PX4/MediaMTX. Обязательные сценарии: geometry control points; точки маршрута/ревизии; resize/focus/bounds окон на 1280×720 и 1440×900; reconnect/reset generations; полёт/Offboard failsafe; реальный decoded WebRTC кадр; все lifecycle операции. Интеграционные проверки миров запускать по очереди в Docker.
