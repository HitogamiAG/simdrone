# Проверка PX4 Hub после прототипа

Статус 02.10.2026: перечисленные ниже дополнительные этапы проверены; `run-compose.sh` прошёл целиком (18 тестов Hub, реальная интеграция/отказы/shutdown, 15 тестов Gazebo и regression/smoke). Непроверенные границы указаны в конце документа и README.

Повторная точечная проверка 03.10.2026: Docker Hub contract suite — **21 passed**. Добавлен случай, когда snapshot параметров не читается перед restart: monitor остаётся активным, а последующее падение PX4 завершает пару процессов и переводит instance в `failed`. Сквозная Backend-интеграция также подтвердила штатный stop/start/restart с сохранением параметров.

Исходный план Docker-прототипа находится в постановке задачи. Этот файл фиксирует дополнительные проверки и их границы; успешные тесты с подменёнными адаптерами не считаются проверкой PX4/Gazebo.

| Этап | Изменение и критерий |
| --- | --- |
| Конкурентность | Общий lock операций каждого instance: start, restart, delete, параметры и cleanup после падения. Тесты настоящего `InstanceService` с подменёнными адаптерами: конкурентные слоты, конфликт привязки, лимит, повторное выделение, отказ/таймаут/отмена старта, отказ и повторный restart, PATCH одновременно с restart/delete, частичный отказ параметров. |
| WebSocket | Подписка принадлежит конкретному объекту fanout; смена поколения закрывает старый WS с `1012`, в том числе при заблокированной отправке. Отключение клиента освобождает буфер; закрытие fanout будит ожидающих клиентов. |
| Диагностика | Connection из MAVSDK core, свежесть по типам, ошибки потоков, health `is_armable`. Валидность привязки отдельно от ошибок процессов: true/false/null; причина очищается при восстановлении наблюдения. |
| Буферизация | По одному ожидающему сообщению каждого типа для каждого клиента; частые измерения не вытесняют редкие. |
| Реальная интеграция | Конкурентный старт двух SITL, третий и отказ четвёртого; разные system ID, независимые параметры, сохранение после restart, WS с медленным клиентом, pause/resume, убийство PX4/MAVSDK, независимость соседа, stop → drone/world reset → create, исчезновение модели. |
| Compose и shutdown | Остановка Gazebo при живом instance: зависимость недоступна и привязка неизвестна. Остановка Hub с живой парой: exit code 0 или 143 (штатный SIGTERM Uvicorn), лог `Application shutdown complete`, PID контейнера 0, после старта того же контейнера реестр и каталоги пусты. Затем последовательный прогон Gazebo contract/regression/smoke. |
| Отчёт | В README указать команды, фактические результаты, время старта и CPU/память Hub для двух/трёх SITL. Замер ресурсов на 5 секунд не является оценкой максимальной нагрузки; Gazebo измеряется отдельно. |

### Дополнительная регрессия restart

При ошибке чтения parameter snapshot restart оставляет процессы запущенными, сохраняет монитор и состояние `running`. Отдельный тест проверяет, что последующее завершение PX4 всё ещё приводит к остановке MAVSDK и состоянию `failed`.

Запуск всей проверки из корня: `sh px4-hub/tests/run-compose.sh`. Нужны работающие Gazebo Service и MediaMTX, исходный мир `empty` без дронов и пустой реестр Hub. Скрипт меняет мир и временно останавливает сервисы; конкурирующие клиенты во время проверки не допускаются.

Границы: Flight API и общий backend не входят в поставку. Согласованный reset проверяет тестовый клиент, атомарность между сервисами не обеспечивается. Тест медленного WS проверяет независимость читателей; принудительный backpressure дополнительно проверяется подменённым WebSocket. Настоящий отказ запуска PX4 из-за испорченного образа и повторная сборка без кеша относятся к отдельной проверке окружения.
