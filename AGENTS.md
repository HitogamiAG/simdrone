# Инструкции для работы с репозиторием

## Цель и стек

Создать платформу создания миссий и их выполнения дронами на базе виртуального мира Gazebo.
Целевой стек: **Gazebo + PX4 SITL + MAVSDK + FastAPI & React**.
Текущая поставка содержит Gazebo API (`gazebo-service`), PX4 SITL/MAVSDK gateway
(`px4-hub`), общий API-оркестратор (`backend`) и видеопубликацию через MediaMTX.
React, Flight API, ручное управление и missions пока не реализованы.

## Рабочий процесс

- До изменений прочитать README затрагиваемого сервиса, соответствующий план в `docs/` и проверить `git status`. Сохранять чужие незакоммиченные изменения.
- После каждого завершённого логического изменения **обязательно выполнять Git-коммит**. Включать только файлы своей задачи; сообщение должно объяснять изменение. Не откладывать все коммиты до завершения большой задачи. Если коммит невозможен, сообщить причину.
- Перед коммитом проверить diff и выполнить проверки, соответствующие изменению. После существенных изменений обязательно прогонять тесты. Изменения API, конкурентности, Transport, reset, подписок и управления процессами считать существенными.
- При существенных изменениях сервиса обязательно обновлять **README.md этого сервиса**: API, конфигурацию, запуск, архитектуру, ограничения и проверенное поведение. Документация, реализация и статус плана должны соответствовать друг другу.
- При выполнении плана проверять его критерии завершения. Прошедшие тесты не заменяют проверку архитектурных требований. Не объявлять этап выполненным при известных расхождениях.
- Не менять публичный контракт и reset-семантику незаметно в рамках рефакторинга. Такие изменения явно описывать и проверять.

## Проверки и запуск

Gazebo на хосте отсутствует: тесты сервиса и проверки симуляции выполнять **в Docker**.
После изменений приложения или тестов сначала пересобрать образ и обновить контейнер, чтобы тестировать текущий код:

```sh
docker compose build gazebo-service
docker compose up -d --no-deps gazebo-service
docker compose exec -T gazebo-service pytest -q /opt/uav/tests/test_contract.py
docker compose exec -T gazebo-service python /opt/uav/tests/regression.py
docker compose exec -T gazebo-service python /opt/uav/tests/smoke.py
docker compose config --quiet
```

При первой поставке или изменениях обоих образов использовать `docker compose up -d --build`.
Интеграционные скрипты изменяют и сбрасывают мир: запускать последовательно, без конкурирующих клиентов.
Для изменений только документации достаточно проверки ссылок и diff; полный прогон симуляции не требуется.
В отчёте указывать выполненные команды, результаты и непроверенные сценарии. Не выдавать подменённый Transport за проверку реального Gazebo или видео.

## Архитектура и инварианты

- `main.py` отвечает за сборку FastAPI и lifespan; маршруты — за HTTP/WebSocket; доменные сервисы — за сценарии; адаптеры — за Gazebo Transport и процессы. Передавать зависимости явно, избегать глобальных singleton и динамической переадресации методов между сервисами.
- Один мир и один HTTP worker для текущей реализации. Не включать несколько workers без пересмотра владения процессом и общим состоянием.
- Подтверждать изменения наблюдаемым состоянием Gazebo. Ответ о принятии команды не означает её применения. `scene/info` и экспорт SDF не считать источниками актуальных runtime-поз и настроек physics.
- Поза дрона задаётся при создании; публичного PATCH существующей позы нет. Drone-reset пересоздаёт модель и PX4 с сохранением публичного `drone_id`, возвращает начальную позу, исходные настройки сенсоров и параметры PX4 по умолчанию. World-reset/reboot восстанавливают исходный SDF и удаляют все runtime-дроны вместе с их PX4; автоматически не пересоздавать их.
- Изменение мира в Backend выполняет world-reset, затем применяет объединённые текущие и переданные настройки. Изменение настроек сенсора выполняет полный drone-reset до запуска PX4. Изменения разрешённых параметров PX4 физический reset не вызывают.
- Backend — единственный публичный владелец соответствия `drone_id` ↔ Gazebo-модель ↔ PX4 instance; реестр живёт в памяти и не восстанавливается после перезапуска Backend. Изменяющие сценарии Backend сериализуются одним lock. PX4 Hub отдельно сохраняет runtime-параметры при stop/start/restart; drone-reset создаёт новый instance с defaults.
- WebRTC камеры обслуживает MediaMTX через WHEP; проверка считается успешной только после приёма и декодирования браузером реального кадра. RTSP/H.264 smoke-тест сам по себе этого не подтверждает.
- Каждый процесс, Transport-подписка, поток и лог имеют одного владельца и идемпотентное освобождение. Проверять cleanup при ошибке старта, reset, reboot и shutdown.
- Сохранять общий порядок блокировок: lock операции → локальный lock сенсора/позы. Закрытие handles сериализовать с изменениями подписок. Callbacks не берут общий lock и не выполняют блокирующие запросы.
- Блокирующие Transport-запросы и ожидания выполнять вне event loop; сохранять нативный GIL-адаптер. asyncio-очереди изменять через их loop; очереди кадров и измерений ограничивать.
- При смене поколения мира и reset инвалидировать старые callbacks, handles и кеши. Камеры передавать через FFmpeg/MediaMTX; обычные сенсоры — через общий Transport-поток и WebSocket.
- Не редактировать сторонние ресурсы без необходимости. Версии образов, зависимостей и commit ресурсов фиксировать; изменения этих версий объяснять.

## Безопасность и границы задачи

- Не коммитить `.env`, пароли, токены, логи, видеозаписи и артефакты сборки. Новые параметры документировать в `.env.example` без секретов.
- API принимает модели из каталога: не добавлять произвольные пути или загрузку SDF без отдельной задачи.
- Не выполнять разрушительные Git-операции и не публиковать/не отправлять изменения в remote без поручения пользователя. Требование коммита само по себе не разрешает push.
- Документацию и отчёты вести на русском; идентификаторы кода и протоколов сохранять на языке проекта.
