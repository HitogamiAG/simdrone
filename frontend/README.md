# Frontend платформы дронов

React 19 + TypeScript 7 + Vite 8, Mantine 9, Three.js / React Three Fiber, react-rnd, TanStack Query и Zustand. Детали интерфейса и известные ограничения: [`docs/frontend-plan.md`](../docs/frontend-plan.md).

## Запуск

```sh
npm ci
npm run dev
npm test
npm run build
```

Vite слушает `0.0.0.0:5173` и проксирует `/api` и WebSocket в Backend `localhost:8003`. Production образ собирает приложение и раздаёт его nginx на порту 80; Docker Compose публикует порт 3000. Nginx проксирует `/api` в Backend. MediaMTX WHEP остаётся прямым адресом.

Vitest + React Testing Library выполняют компонентные проверки в jsdom. Playwright входит в стек; браузерные интеграционные сценарии запускаются против production frontend и работающих сервисов.

## Реализовано

Одно desktop workspace: сворачиваемая панель, accordion для дронов/миссий/мира, запросы к read API, общий realtime WebSocket для поз дронов и PX4 телеметрии, pause/resume симуляции и оболочка resizable окон. Клиент считает подписчиков по каналам, обрабатывает protocol ACK, повторяет действующие подписки после reconnect и invalidation. Карта и окно телеметрии получают собственные каналы через общий клиент; REST-поза используется до первого realtime-образца. Локальные `world.glb` и manifest пакета `empty` подключены к React Three Fiber: версия сверяется с Backend, `glb_to_gazebo` применяется один раз, 2D/3D камеры, zoom/fit и слои площадок/дронов отображаются в браузере. Площадки выбираются в диалоге и кликом на карте; направление spawn-frame и owner видны.

Создание дрона подключено к `/api/v1/world/spawn-pads`: форма требует явный выбор доступной площадки и отправляет `spawn_pad_id`; занятые площадки показывают владельца, координаты доступны только для чтения, конфликты приводят к обновлению каталога. Список дронов показывает закреплённую площадку. Пакет `empty` версии 1.1.0 включает две площадки. Сцена проверена в Chromium при 1440×900 с mock Backend ответами: загружен настоящий локальный GLB, переключены 2D/3D камеры, выбор маркера открыл форму с площадкой. Дополнительно production frontend открылся в Chromium с реальным Backend, показал GLB-карту и площадки без browser errors; на момент проверки дронов не было. Браузерная приёмка поз с настоящим Gazebo/PX4 и координатная точность 2 см остаются открытыми.

Окно телеметрии показывает pose Gazebo и последние образцы PX4 (позиция, скорость, ориентация, режим, armed/landed, GPS, health, батарея при наличии); оно держит свою подписку даже в свёрнутом состоянии и освобождает её при закрытии. Окно логов получает live stdout/stderr PX4, показывает источник и время, поддерживает поиск, паузу отображения, автопрокрутку и очистку; буфер ограничен 2000 строками на дрон. Backend не предоставляет replay, поэтому окно показывает строки с момента подписки. Окно видео использует WHEP и освобождает AbortController, RTCPeerConnection и серверную сессию при сворачивании/закрытии. Во время browser acceptance подтверждены настоящие строки PX4 и декодированный кадр 640×480.

Редактор миссий подключён к публичному Backend API: создание черновика, выбор записи, изменение параметров и упорядоченных XYZ точек, сохранение с `expected_revision`, проверка, запуск и отмена с подтверждением. Локальные изменения не перезаписываются фоновым обновлением; при 409 черновик сохраняется, серверная версия перечитывается только по явному действию. Активный маршрут и режим добавления/перемещения точек отображаются на общей 2D/3D сцене. Реальный браузерный путь миссии ещё требует повторной приёмки.

Ручное управление подключает отдельную Offboard WebSocket-сессию, ограничивает ввод явным захватом, отправляет команды с возрастающим `seq` с частотой 20 Гц, обнуляет скорости при отпускании и потере фокуса. Есть экранные кнопки, arm/disarm с проверкой посадки, RTL/посадка, watchdog-подсказки и подтверждение закрытия активной сессии. Реальный браузерный канал подтвердил ненулевые setpoints и переход PX4 в OFFBOARD; возвратом удалось вернуть состояние на землю в отдельном прогоне.

Настройки дрона позволяют менять поддерживаемые PX4 параметры, сенсорные частоты/reset, останавливать/запускать/перезапускать PX4 и выполнять drone-reset. World modal управляет physics, gravity, геопривязкой, pause/resume, reset и reboot. Логи Gazebo мира открываются в отдельном окне из блока настроек мира через общий канал `world.logs`; закрытие окна освобождает подписку. Деструктивные lifecycle-команды подтверждаются; после операций UI перечитывает дронов и площадки. Проверено в браузере: PX4 stop/start/restart, sensor rate/reset, drone reset с сохранением площадки и начальной позы, world patch/reset, reboot, pause/resume. Ввод вне допустимого диапазона 26 Гц при максимуме 25 Гц оставил диалог открытым с ошибкой API.

Менеджер окон сохраняет координаты, размеры и сворачивание в localStorage, восстанавливает окна только для существующих дронов и удерживает заголовки в пределах карты при resize. В Chromium проверен drag/resize/reload и bounds на 1280×720; видео также проверено на 1280×720.

Полётную browser-приёмку считать не пройденной. Из production UI миссия прошла Backend validation и перешла в execution `preparing/takeoff`, однако Gazebo pose резко ушла с площадки до сотен метров по высоте; PX4 сообщал `TAKEOFF` и armed, а execution не продвинулся к первой точке. После RTL положение продолжало расти. Дрон был удалён через UI, PX4 остановлен и площадка освобождена. В этом runtime `simulation.paused=false`, но API показывал `real_time_factor=0.0` при продолжающемся изменении sim_time; необходимо отдельно исправить/исследовать физику и сопоставление поз с PX4 до повторной лётной приёмки. Пространственная проверка GLB/Gazebo с допуском 2 см также не выполнена.
