# Проверка результата рефакторинга

Дата: 2026-10-02. Проверен код относительно [плана](refactoring-plan.md).

**Вывод: рефакторинг выполнен частично.** `main.py` сокращён до 41 строки, выделены routers, конфигурация, данные, Gazebo-адаптеры и владельцы подписок/кодировщиков. Текущие контейнерные тесты проходят, но требование удалить временный facade и явно разделить зависимости не выполнено. Найден воспроизводимый дефект конкурентного освобождения подписки.

## Замечания

### 1. Высокий приоритет: закрытие WebSocket обходит общий lock

`SensorSubscription.close()` напрямую вызывает `SensorHub.unsubscribe_queue()`. Этот путь не использует общий lock операций, хотя обёртка `SensorsOperations.unsubscribe_queue()` сериализована. WebSocket в `finally` вызывает именно `handle.close()`.

В `release_subscription()` проверка отсутствия потребителей и снятие Transport-подписки не атомарны относительно подключения нового клиента. В контейнере с подменённым клиентом и двумя потоками воспроизведён порядок:

1. Последний старый клиент закрывается; Hub видит пустой список потребителей и начинает unsubscribe.
2. Новый клиент под общим lock добавляет очередь. `ensure_subscription()` видит прежнюю запись подписки и не создаёт новую.
3. Старое закрытие завершает unsubscribe и удаляет запись подписки.

Результат: очередь нового клиента существует, а Transport-подписка отсутствует. Измерения больше не приходят. Это нарушение инварианта конкурентности из плана, а не только вопрос структуры кода.

Исправление: выполнять весь lifecycle подписки, включая закрытие handle, под общим lock; сохранить порядок lock операции → sensor.guard. Добавить детерминированную проверку такого пересечения закрытия и открытия клиента.

### 2. Средний приоритет: временный facade остался

`RuntimeCoordinator.__getattr__()` перебирает сервисы, переадресует методы PoseTracker и раскрывает общие словари. `__setattr__()` перенаправляет записи в SessionState. Каждый сервис наследует `ServiceContext`, который передаёт неизвестные обращения обратно в runtime.

Маршруты вызывают бизнес-методы на runtime через этот механизм. `api/dependencies.py` создан, но маршруты им не пользуются. Сервисы продолжают обращаться к чужим приватным методам через неявный общий контекст.

Это прямо противоречит этапу 8 «удалить временный facade» и требованию явных зависимостей. Файлы стали меньше, но границы сервисов остаются неявными: опечатки, пересечения имён и недостающие зависимости обнаруживаются только во время выполнения.

Исправление: явно передать сервисам state, client/provider, tracker, catalog и необходимые соседние сервисы; маршрутам передавать соответствующий сервис. Coordinator оставить сборку и lifecycle. Удалить динамический поиск методов и неиспользуемые импорты/дубликаты. SessionState переместить в `entities.py`, как предусмотрено планом.

### 3. Средний приоритет: SensorService зависит от камер

`SensorsOperations._sensor_json()` читает `camera_procs` и собирает RTSP URL. `SensorHub.ensure_subscription()` тоже читает реестр камер. Доступ скрыт динамическим facade; при этом CameraService уже использует SensorService.

План явно требует обратной зависимости не вводить и добавлять статус камеры через presenter с публичным статусом CameraService. `services/cameras.py` вместо `media/cameras.py` само по себе не является существенной проблемой; важна фактическая зависимость и владение состоянием.

Исправление: вернуть SensorService ответственность за сенсоры; статус камеры получать из публичного интерфейса CameraService на уровне сборки ответа. Владение подпиской камеры согласовать явно, без чтения чужого реестра процессов.

### 4. Средний приоритет: teardown EncoderSession не подтверждает принудительное завершение

В `EncoderSession.stop()` после второго таймаута вызывается `process.kill()` без последующего `wait()`. `stderr` явно не закрывается; завершение writer ограничено `join(timeout=1)` без проверки результата.

По коду аварийный teardown не гарантирует, что процесс собран и поток завершён к моменту возврата. Штатные тесты cleanup проходят; аварийный сценарий здесь не воспроизводился. Существующий unit-тест проверяет только уже завершившийся fake process, поэтому ветку SIGKILL не покрывает.

Исправление: после kill дождаться процесса, закрыть принадлежащие session дескрипторы, подтвердить завершение writer и проверить ветки таймаутов/ошибок. Не скрывать отказ освобождения ресурсов.

### 5. Средний приоритет: проверок недостаточно для закрытия всего плана

README честно перечисляет отсутствующие сценарии: авария FFmpeg, независимые одновременные камеры, два RTSP-читателя и медленный WebSocket-клиент. Они перечислены среди проверок этапов 6–7 плана, поэтому полный статус «реализован» преждевременен.

Также текущий OpenAPI-тест проверяет наличие нескольких маршрутов, а не весь сохранённый контракт; результат успешного smoke не подтверждает совпадение всех JSON-ответов с исходной версией. Прогон существующего образа не является проверкой сборки с нуля.
